# Handoff SM-T585 — DSI re-enable after blank

## Charter
- Scope: SM-T585 (gtaxllte), mainline 7.3 fork (`src/mainline`, branch `gtaxllte`), pmOS + GNOME Mobile.
  Goal: the display comes back after blank (GNOME power key short press, idle blank), so the
  power key gets its standard behaviour.
- Terms: *blank/unblank* = DRM disable/enable of DECON → DSIM → panel; *stuck* = a packet header
  stays in the DSIM header FIFO; *re-enable* = any enable after the first one since boot.
- Mode: interactive with the user. Plan first, one variable per experiment, prediction written
  down before each run. Root on the tablet: see CLAUDE.local.md.

## Conclusions (what holds now)
- Installed: linux-samsung-gtaxllte r8 (#9) = everything committed (2b battery data, CMA 128 MiB,
  accelerometer matrix diag(-1,-1,-1)). No test files on the tablet. Interim for the user: GNOME
  "Blank Screen: Never", do not press the power key.
- Blank works. Unblank: the first panel command after re-init stays in the header FIFO
  (FIFOCTRL 0x00011157: one header, empty bit clear). Mainline does not wait for the FIFO on 7870,
  so later writes overflow it → SError in `samsung_dsim_transfer_start` → panic.
- First boot works only because the bootloader left DSIM/DECON configured and running.
- 7870 FIFOCTRL: header empty/full = bit 10/11 (downstream `regs-dsim.h`); mainline uses 22/23 for
  all variants, which is why `wait_for_hdr_fifo = 0` for 7870. Fixing the bit makes the wait work
  (prevents the crash) but does not make the packet leave.
- In the stuck state: PLL stable (LINK_STATUS bit 24), data lanes in stop state, SHADOW_EN = 0
  (shadowing is not involved), CONFIG has VIDEO_MODE (bit 18), SFRCTRL STANDBY = 0,
  MDRESOL/porches = 0 (mainline sets them only in atomic_enable).
- Downstream order (`decon_7870/dsim_reg_7870.c` `dsim_reg_init`, `dsim_drv.c` enable):
  clocks/lanes → config (incl. video mode) → resolution + porches → shadow off → `dsim_reg_start`
  (HS clock + STANDBY) → panel init commands → DECON start. On disable in video mode it sends no
  panel commands: stop link, cut panel power.
- Experiments so far (test kernel, fb0 blank/unblank over ssh):
  | # | change | result |
  |---|---|---|
  | 1 | 20 ms delays in resume, init, around each FIFO write | 1 cycle OK |
  | 2 | delay only after phy_power_on | crash |
  | 3 | delays only in init | crash |
  | 4 | wait_for_hdr_fifo=1 with bit 22 | every wait times out (slow boot) |
  | 5 | bit 10 + wait + SFR STANDBY set in init | 3/3 OK, 1 timeout per cycle |
  | 6 | 5 + STANDBY cleared in post_disable | 3/3 OK, 3 timeouts at blank |
  | 7 | bit 10 + wait + VIDEO_MODE only while enabled | cycle 1 OK, cycle 2 stuck |
  Patch of the last state: `kernel/out/dsi-reenable-wip.patch`; dumps `kernel/out/dsim-*.txt`.

## Debug plan
Hypotheses (each with the experiment that separates it and the prediction):
- **H1 – lost state:** runtime suspend (PHY off/reset via DISP sysreg, clocks) drops something
  the bootloader set and `samsung_dsim_init` does not restore.
  Test A: keep the DSIM runtime-active across blank (no suspend between disable and enable).
  Predict: H1 → unblank works without any other change; not H1 → stuck as before.
- **H2 – incomplete init before commands:** in video mode the DSIM needs resolution, porches and
  STANDBY programmed before it sends commands (downstream order).
  Test B: for 7870, program display mode (resolution/porches) and STANDBY at the end of
  `samsung_dsim_init`, as `dsim_reg_init` + `dsim_reg_start` do; keep the FIFO-bit fix.
  Predict: H2 → 10/10 cycles, zero FIFO timeouts; partial → timeouts remain at blank (then add
  "no panel commands after DECON stop", downstream style).
- **H3 – mode switching:** toggling VIDEO_MODE while the link runs is not reliable (exp. 7).
  Only if B fails: Test C = mode switch only with the link idle/reset. Predict: H3 → 10/10.
- Excluded: PLL lock, PHY settle time, clock gating (clk_summary unchanged), shared LDO35
  (always-on), shadow registers, power domains (none in the DTSI).

Order and method:
0. Diagnostic kernel first (no fix): register snapshots (CONFIG, SFRCTRL, MDRESOL, porches,
   LINK, DPHY, FIFOCTRL, ESCMODE) at fixed checkpoints — end of init, before and after the first
   packet — on the first enable after boot AND on re-enable; FIFO-bit fix on, wait timeout
   lowered to 50 ms so nothing hangs. The diff first-boot vs re-enable at the same checkpoint
   decides between H1 and H2 before any fix is tried.
1. Test B (most likely, mirrors downstream), then A, then C.
2. Accept a fix only after: 20 fb0 blank/unblank cycles, 5 GNOME power-key cycles, zero FIFO
   timeouts, no WARN/SError. Then 2 separate patches: FIFOCTRL bit (upstream-worthy alone) and
   the init/enable order.

Test infrastructure:
- Separate build dir for test kernels with `CONFIG_MODULE_ALLOW_BTF_MISMATCH=y` (otherwise every
  package module fails BTF validation, including the charger); package builds stay untouched.
- `panic=5` on the pmos.conf options line during tests (auto-reboot, pstore keeps the trace);
  `/boot/vmlinuz.good` = package kernel; restore = copy back + reboot; a package install rewrites
  pmos.conf.
- Wait loops: always with a timeout and a check of the real state (uname -v, uptime).
